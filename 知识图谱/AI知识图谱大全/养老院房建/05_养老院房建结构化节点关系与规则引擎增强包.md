## 二、统一节点字段规范

所有节点按以下字段理解和导出：

| 字段 | 含义 | 默认规则 |
|---|---|---|
| node_id | 节点唯一ID | 沿用 `SEN-*`、`AI-SCORE-*`、`TAB-*`、`KG-*` |
| node_name | 节点名称 | 优先使用 Markdown 标题或评分项名称 |
| node_type | 节点类型 | construction_process、eldercare_function、accessibility_control、quality_control、safety_control、score_item、template、rule_placeholder、language_guardrail 等 |
| domain | 专业领域 | senior_care_building_construction |
| evidence_level | 证据等级 | 通用节点默认 A_secondary；占位规则 A_pending；正式项目文件进入后 A_primary |

| source_required | 是否需要正式来源 | A_pending 必须 true；A_secondary 默认 false |
| keywords | 关键词 | 用于 GPT Knowledge 召回 |
| synonyms | 同义词 | 用于中文变体和评标表达召回 |
| score_keywords | 评分关键词 | 施工方案、质量保证、安全文明、绿色施工等评分项识别词 |
| industry_keywords | 行业关键词 | 养老院、照护单元、适老化、护理型床位等行业识别词 |

| applicable_condition | 启用条件 | 对应工程对象、养老功能、评分项或项目要求 |
| required_response | 必须响应内容 | 采用“问题—措施—参数—验收—证据”五段式闭环结构 |

## 三、重要节点问题—措施—参数—验收—证据模板

所有重要技术节点、评分节点和风险节点按以下结构生成响应。若项目缺少正式参数，参数栏写“按图纸/规范/招标要求，需补充具体数值”，不得虚构。

| 步骤 | 输出要求 | 养老院房建示例 |
|---|---|---|
| 第一步：问题 | 说明服务的评分项、章节、工程对象和主要风险 | 无障碍不连续、消防联动资料缺项、扶手固定不牢、呼叫点位漏设 |
| 第二步：措施 | 写明责任主体、施工部位、工艺流程和检查频次 | 由专业工程师、质检员和班组长按样板、隐蔽、检验批、移交前分阶段检查 |
| 第三步：参数 | 写明图纸、规范、专项方案或项目要求中的控制标准；缺少依据则标注需补充 | 坡度、净宽、安装高度、试压压力、照度、风量等以正式资料为准 |
| 第四步：验收 | 写明验收方法、检测方式、整改复核和关闭条件 | 样板验收、蓄水试验、消防联调、无障碍体验复核、房间移交验收 |
| 第五步：证据 | 写明留痕资料、表格编号和溯源位置 | `TAB-SEN-WC-01`、`TAB-SEN-CALL-01`、旁站记录、检测报告、影像资料、培训签到 |

## 四、关系边类型库

| relation_type | 含义 | 使用场景 |
|---|---|---|
| belongs_to | 属于某模块 | 节点属于适老化、消防、机电、运营移交等模块 |

| checked_by | 由审查节点检查 | 输出内容由暗标/雷同/事实边界检查 |

| upgrade_to_primary | 取得正式文件后升级 | 占位规则升级为 A_primary |
| linked_to_template | 关联输出模板 | 节点绑定表格或正文模板 |
